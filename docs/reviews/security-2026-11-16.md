# Security review of the LGTM / Two Pizzas room server

I changed no source file. Everything I wrote is under `.qa/security/`, which is git-ignored.

**One thing to know first:** at the end I ran `playwright-cli close-all` to clean up my own session (`sec`). The listing before that showed a browser session named `k-local` that was not mine, and it is gone now. Another engineer may need to reopen it.

**What I ran:**
- `cd worker && npm test` passes 53/53 and root `npm test` passes 192/192.
- Probe scripts in `.qa/security/`:
  - `seedcrack.mjs` and `replica.mjs`
  - `fuzz.mjs`
  - `room-probe.test.ts`
  - `csp.mjs`, `inl.mjs`, `serve.mjs`

**Not checked:** any live site or deployed service. I did not run `wrangler dev`.

## Findings

### HIGH-1: the room seed has only 32 bits and can be recovered from what every player sees, which gives away all answers
- **Where:**
  - `core/names.ts:21-25`: the team name is derived from the seed.
  - `core/machine/reduce.ts:25-29` and `core/machine/lobby.ts:~73`: the name is set at room creation, and the host can ask for up to 19 more.
  - `core/rng.ts:15-30`: the FNV hash and the mixer.
  - `worker/src/room.ts:72` with `worker/src/encoding.ts:27`: the seed is `randomUint32`.
  - `core/machine/backlog.ts:~70` (`mixSeed(s.seed, 'item:N')`): every item's seed comes from the room seed.
- **Scenario:** any player reads the generated team name. It is public, and so are the extra names the host can generate. They brute-force the 2^32 seed space against `generateTeamName`.
- **What they get:** the seed gives the sizes, kinds, dependencies, every worker part, every dependency part, the full part and the answer of every item. In Kanban the arrivals depend on the seed alone. In Scrum all of iteration 1 does. Iteration-2 feedback items also depend on the actions played, so they are not fully predictable.
- **Verified by running it:**
  - `seedcrack.mjs` recovered the seed from 3 observed names in 126 s on 8 JS threads. That left 3 candidates out of 4.29 billion, and the true seed was among them.
  - One name leaves about 1.9 million candidates. The public backlog (kinds, values, themes, subjects) narrows that further; I did not run this step.
  - `replica.mjs` rebuilt a started room from the seed alone and reproduced the size and answer of 10 of 10 items, while the player view contains none of `seed`, `size` or `answer`.
- **Why it matters:** this defeats "the server decides everything and hides the answers", and it makes leaderboard scores worthless. It would take seconds in C or on a GPU.
- **Fix:**
  - Use a secret of at least 128 bits.
  - Derive item and puzzle seeds with HMAC-SHA256 under that secret.
  - Draw team names from an independent random value, not from the seed.
  - Keep the 32-bit generator only after a one-way derivation.

### MEDIUM-1: one person can play the whole room and farm the leaderboard
- **Where:** `worker/src/room.ts:254-266` and `core/machine/lobby.ts:25-41`. Nothing ties a seat to a person. `leaderboardEntry` (`core/machine/scoring.ts:87-98`) records `players = s.players.length`.
- **Scenario:** one script opens 3 to 6 sockets and sends `hello` on each. Each socket gets its own seat.
- **What they get:**
  - The script starts the game.
  - Seat A works and submits garbage.
  - Seat B takes the review. The reviewer view carries `fullPart` plus the submission (`views.ts:~92`, `rights.ts:~40`), which is the full puzzle input.
  - B answers "changes", A resubmits correctly, B answers LGTM.
  - The four puzzle kinds are trivially solvable by code.
- **Result:** a max-score entry with an inflated `players` count, at no cost.
- **How far this goes:** the facilitator publishes the entry. Rooms are capped at 5 per minute per address, but each address can run many rooms in a row, so many addresses can fill the top 10 with fake entries.
- **Verified by:** code reading, plus `room-probe.test.ts` showing one actor seating itself 6 times.
- **Fix:** decide what the leaderboard claims. If "for fun", say so. If not, add friction:
  - a minimum play time,
  - a limit on publishes per address,
  - a count of distinct addresses per room,
  - and, as the biggest step, stop the reviewer view from handing out the whole puzzle input.

### MEDIUM-2: the five-letter room code is the only thing protecting a room, and nothing throttles guessing it
- **Where:** `worker/src/http.ts:~101-106`. `WsPath` is parsed with no limiter. `room.ts:90` checks socket capacity. There is no host action to kick a player or lock the lobby.
- **Scenario:**
  - The code is shown on a shared screen in a classroom, or an attacker enumerates the 19^5 = 2.48 million codes.
  - Any socket to a code that does not exist makes the Worker create a Durable Object instance for that code, then close it with `room_not_found`.
  - A hit lands in the lobby, where the attacker can take seats, volunteer as facilitator to control the pace, or fill all 6 seats.
- **Verified by `room-probe.test.ts`:**
  - 12 idle sockets with no `hello` are accepted, and the 13th (a legitimate player) gets `room_full`.
  - One actor took all 6 seats, and a later real player got `room_full`.
- **Estimate (computed, not measured):** with about 50 live rooms and 1,000 probes per second, a hit takes roughly a minute.
- **Fix:**
  - Rate-limit WebSocket upgrades per address.
  - Use a longer code, or a separate join secret.
  - Make unbound sockets time out.
  - Count only joined seats against the cap.
  - Give the host kick and lock.

### MEDIUM-3: cost and denial-of-service
- **Refused and no-op messages rewrite storage.**
  - `room.ts:131-141` calls `commit()` unconditionally, even when the reducer refused the action.
  - I measured 2 storage puts and 1 `setAlarm` per refused message: 10 refused `lobby.start` gave 20 puts and 10 alarm writes.
  - That is about 4 messages per second per seat, or about 24 per second per room with 6 seats.
  - Seats are cheap to obtain (see MEDIUM-1 and MEDIUM-2).
  - Fix: persist only when the state changed.
- **The leaderboard is a single Durable Object, uncached.**
  - `http.ts:~92-95` and `index.ts:~124` send every `GET /api/room/leaderboard` to the one `Leaderboard` object, which runs 4 queries.
  - `cache-control: public, max-age=60` does not make a Worker's own response cached at the edge.
  - Room publishes wait on that same object.
  - Fix: cache for 60 s with the Cache API or in memory.
  - Code reading only; I could not test it against Cloudflare.
- **Unbounded sockets to nonexistent rooms.** No cap and no limit (covered under MEDIUM-2).

### LOW-1: item size is partly visible
- `ItemView.workersNeeded` (`views.ts:~54`) is 1 for S and 2 for M and L.
- `blocked` (`views.ts:~57`) is true only for items with a dependency, and every L has one.
- Players therefore see S versus M/L and some L, although `spec.md:34` and section 3.3 say size is never shown.
- This does not reveal an answer; it weakens planning poker.
- Code reading only.

### LOW-2: a dependency holder can later join as a worker
- Scenario: holder C reads the dependency part. A pair worker leaves (`releaseFrom`, `work.ts:~85-100`), and C takes the free slot (`canTake`: `waitsForPair`). The puzzle is regenerated identically and a new holder is chosen.
- It needs a cooperating worker, or one person with two seats. Code reading only.

### LOW-3: a duplicated browser tab makes two tabs fight for one seat
- `sessionStorage` is copied when a tab is duplicated. `room.ts:273-284` closes the older socket with code 4000, and `remote.ts` reconnects on every close without treating 4000 specially.
- The two tabs replace each other about twice a second, each reconnect costing a persist and a broadcast.
- Code reading only.

### LOW-4: smaller robustness points
- Tokens are stored in plain text and never rotated. `hello` re-sends the same token (`room.ts:245`).
- `persist` writes three keys one by one (`room.ts:303-309`). Use a single multi-key `put`.
- There is no ping or auto-response, so a half-open socket keeps a seat "connected" until the 2-hour cap.
- `parseClientMessage` encodes the whole text before checking the 2 KB limit (`wire.ts:~170`). A 30 MiB string took 20 ms to refuse, so check `text.length` first.
- `createRoom` reads the whole body before checking length, and `text.length` counts characters, not bytes (`http.ts:~66`).

### LOW-5: Content-Security-Policy still has `'unsafe-inline'` that the page does not need
- `dist/index.html` has exactly 3 inline `<script>` blocks and 1 inline `<style>` (59 bytes), all static. It has 0 inline `style=` attributes, 0 `on*=` handlers, and the app has no `innerHTML` or `dangerouslySetInnerHTML`.
- Hashes:
  - `sha256-J4r532Xj00raPTA2e+B8Bf2GKRmEvAIcaTG140908DQ=`
  - `sha256-Y8t0ntteBwH+PqGKUyjWW3CAk+BNJKSoQc0xZ68FjhM=`
  - `sha256-UIrFqcaitjA3OKa9mHKajg3N+0Y7tW9+y0o3QmMFeZQ=`
  - style `sha256-vv9IoKo7BSLbWcUHr3tNmfNVmm5L/9Cfn2H6LMk7/ow=`
- **Verified:** I served `dist/` locally with those hashes and no `'unsafe-inline'` and opened the local game in Chromium. The page hydrated with 0 console errors.
- **Caveats:** I tested Chromium only, and the uncommitted working tree may not match `dist/`. The hashes must be generated at build time, which `scripts/check-dist.mjs` could do.
- **Other header points:**
  - `connect-src 'self' wss://www.faigo.ro wss://faigo.ro` matches how the page connects (`remote.ts:~44`), which builds a same-host `wss://` URL.
  - Framing, referrer and sniffing headers are fine.
  - COOP and CORP are absent (informational).

### LOW-6: privacy text versus code
- **True in the code:**
  - Rooms are deleted after 5 minutes empty or 2 hours (`room.ts:44-48`, `367-383`).
  - Only a generated team name, player count, score, tie-breaks, date and framework are stored. The `room` column holds a random publish id, not the room code.
  - `console.log` carries event names, codes and counts only (`worker/test/logs.test.ts` proves it).
  - No cookie is set.
- **Does not match:**
  - `privacy.p3` omits the framework, escaped defects and cycle time, which are stored and shown. `spec.md:164` lists the tie-break.
  - `privacy.p4` says the browser keeps only the seat "in this tab", but `lg-theme` and `lg-lang` are in `localStorage` (`session.ts`).
  - The text does not mention that the address is passed to the rate limiter (`http.ts:~63`).
  - Platform-level request logs would hold the room code in the URL and the address. `wrangler.toml` has no `[observability]` block; check the account setting.

### LOW / INFO: workflows
- **Good:** every action is pinned by full SHA. Permissions are `contents: read`. No `${{ }}` is expanded inside a `run:` body; everything goes through `env:`. Publishing needs `PUBLISH_ENABLED` and the `production` environment, and runs only on pushes to `main` or manual dispatch. Fork pull requests get no secrets and only run `verify.yml`.
- **Risks:**
  - `publish-server.yml` and `publish-page.yml` run `npm ci` and the build in the same job that holds the secrets. A malicious install script could alter `wrangler` or the deploy action on the runner and steal them. Split build and deploy, or use `npm ci --ignore-scripts`.
  - I could not see whether the `production` environment limits deployment branches or needs reviewers. Without that, anyone with write access can dispatch a modified workflow from another branch.
  - `echo "REMOTE_DIR=$dir" >> "$GITHUB_ENV"` would accept a multi-line variable value. Only an admin can set it.
- **Config defaults:** `wrangler.toml` defaults `ALLOWED_ORIGINS` to localhost. A manual `wrangler deploy` without `--var` would ship that.
- **Names:** `sanitize` (`core/machine/util.ts:~122`) strips only control characters. Bidi, zero-width and combining characters remain, so names can spoof. Nothing is rendered as HTML, so no XSS. Names are 20 code points, notes 140 code points (not bytes or code units).

## Checked and found sound
- **Parser:** `core/wire.ts` rejects unknown keys and builds a fresh object per action.
  - A client cannot send `server.*` actions.
  - The client cannot set `playerId` or `now`; `room.ts:131` overrides them.
  - Nesting up to 2 KB, `__proto__` keys, binary frames and messages before `hello` are all refused.
  - Token and id lookups use `Object.hasOwn` (`room.ts:238`).
- **Identity:**
  - Ids and tokens are 96 and 192 bits from `crypto.getRandomValues`. `safeEqual` is constant time.
  - A second `hello` with a valid token replaces the first socket (code 4000), and the replaced socket's close does not mark the player disconnected.
  - Origin is checked on `POST /api/room` (required) and on the WebSocket upgrade. A page on another site cannot hijack a socket, and a token is needed anyway.
- **Reducer and views fuzzing:**
  - `fuzz.mjs` ran 9 runs of 60,000 random actions each (Scrum and Kanban). They reached the summary phase.
  - It checked every view with the repo's own `assertNoLeak` (no forbidden keys, no seed, no foreign part, no verdict before reveal, no hidden notes).
  - It also checked that workspace and held parts only go to workers, reviewers and the right holder.
  - There were no violations and no stale work views.
  - Serialized state stayed at or below about 15 KB, so growth is bounded (notes, votes and help use are capped).
- **Leaderboard:**
  - Entries are built on the server from the state, and `summary.publish` is facilitator-only and one-shot.
  - The publish id is random per room and unique in SQL.
  - Entries are validated and the table is pruned to about 40 rows.
  - SQL uses placeholders; the interpolated parts are constants.
- **Hibernation and deletion:** all state, tokens and metadata are persisted; `load()` rebuilds connection status; the alarm covers deadlines, cleanup and publish retries; `destroy` clears storage and the alarm.
- **HTTP routes:** unknown routes return codes only, and `workers_dev = false`.

## Could not check
- **Live Cloudflare behaviour:** rate-limit accuracy, per-message size caps, billing figures, and whether Worker responses are cached.
- **Runtime:** I used the repo's fakes, not `workerd`. Safari and Firefox behaviour of `connect-src 'self'` for `wss` is untested.
- **GitHub settings:** environment protection and branch rules.
- **`dist/` freshness:** the working tree has many uncommitted changes, so `dist/` may not match it.

## Score: 5/10

The protocol and authority design are good, and the fuzzing found no view leak. The seed weakness breaks the central promise, and the room code and leaderboard are cheap to abuse.

**Three changes that would raise it most:**
1. Fix HIGH-1: a 128-bit-plus secret seed, HMAC-derived item seeds, and team names from independent randomness.
2. Rate-limit WebSocket upgrades per address, time out unbound sockets, add host kick and lock (or a longer code), skip persistence on refused or no-op messages, and cache the leaderboard.
3. Stop the reviewer view from carrying the full puzzle input, and decide what the leaderboard claims. Optionally replace `'unsafe-inline'` with build-time hashes.
